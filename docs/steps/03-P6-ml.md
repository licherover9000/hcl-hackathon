# Step 03 (P6): Miss-next-instalment model, evaluation and scoring service

**Owner:** AI/ML · **Status:** done; tested on synthetic data shaped like the case files (must be rerun on the real files)

## Summary
Trains a logistic regression that predicts whether a loan's next instalment will be missed, compares it with gradient boosting and the bucket-miss-rate baseline, writes the evaluation report and model card, scores the current book with the top 3 reasons per loan, and serves scores over HTTP for the backend.

## Files
| File | Role |
|---|---|
| `ml/common.py` | Feature lists (categorical, numeric, excluded), plain-language reason templates, contribution-based explanations |
| `ml/train.py` | Time-based split, training, metrics, calibration, fairness, model card, current-book scores |
| `ml/serve.py` | FastAPI: `/health`, `/score`, `/score/rows` |
| `ml/requirements.txt`, `ml/README.md` | Setup and commands |

## How it works
1. Load `training_snapshots`, split by snapshot_date (train ≤ 2025-11-30, test 2025-12-31 to 2026-02-28).
2. Pipeline: median imputation + scaling for numbers, one-hot for product, occupation_type, bucket; LogisticRegression (seed 42).
3. Metrics on test months: ROC-AUC, PR-AUC, Brier, precision at top 20%, precision and recall at 0.60, ROC-AUC on CURRENT only, vs the bucket baseline.
4. Calibration table (10 bins) and fairness tables by city_tier and occupation_type (R13 flag rate ratio, flagged if below 0.8).
5. Score `features_current`, write `output/ai_scores.csv`; the Java day-end adds expected_recovery = (1 − p) × (overdue + EMI) and ai_rank, and applies R13.

## Design decisions
- **Logistic regression served, boosting as comparison:** explanations are exact and easy to defend; trees may score slightly higher but explanations need SHAP.
- **Time-based split:** a random split would leak future months into training.
- **AI only orders and suggests reminders:** rules stay authoritative; fallback to rules order when the service fails.

## Tested
On synthetic data (18,000 snapshots, 2,310 current loans): pipeline runs end to end, report and model card written, service returns scores for given loan ids. Example 14 through the Java pipeline: p = 0.65 gives expected_recovery 3,588.55, PRE_DUE_REMINDER, AUTO_DIGITAL, EARLY_WARNING_AI.

## Change scenarios
1. Remove `missed_6m` from NUMERIC: model retrains without it, ROC-AUC likely drops; report shows the new number.
2. Raise the R13 threshold to 0.7 in rules config: fewer CURRENT loans get pre-due reminders; the model itself is unchanged.
3. Stop the service: the backend logs the failure, keeps rules order, UI shows "AI ranking unavailable".
